# 橱窗销售脉冲反馈设计

**日期：** 2026-07-10  
**状态：** 已确认  
**范围：** 基于当前主界面左右布局，强化橱窗自动成交与集中收银的反馈爽感。

## 1. 背景

游戏的核心乐趣应集中在左侧橱窗：玩家通过商品摆放形成位置、相邻、套装、成长、主题、道具与冲突等增益/减损，再从真实售卖结果中感受到布局价值。

当前工程已经具备以下基础：

- `scenes/Main.tscn` 使用约 `63%` 左橱窗、`37%` 右工作台的常驻左右结构。
- 右侧工作台保留 `采购 / 产出 / 研发制作 / 橱窗经营` 四个页面。
- 左侧 `ShowcasePanel` 使用 `10x10` 橱窗棋盘。
- `_process()` 每秒检查到期商品，`_sell_ready_showcase_slot()` 完成真实自动成交。
- 自动成交已经立即增加金币、口碑，并推进任务、配方成长和营业记录。
- `ShowcaseRuleService`、`ShopSimulation` 与配方成长服务已经能提供售价、售速和正负原因。
- 橱窗经营页已经拆分为经营概览、结算到期、当前加成、最近收银、经营风险、橱窗扩张等独立分区。

现有反馈的主要问题不是“没有数值”，而是数值仍以 tooltip、文字摘要和记录为主。玩家能读懂结果，但没有充分感受到“这个摆法正在爆单”。

## 2. 设计目标

### 2.1 核心目标

- 保持布局解题与售卖收获各占一半，但把主要情绪峰值放在售卖阶段。
- 让每次成交能回答三个问题：哪件商品卖了、赚了多少、为什么赚得更多或更少。
- 用持续的小成交脉冲制造节奏，用手动集中收银制造阶段性高潮。
- 负面反馈清晰可见，但表达为可优化机会，不制造失败或破产压力。

### 2.2 非目标

- 不改成独立收银页面或全屏营业弹窗。
- 不改变左橱窗、右工作台的主结构和四个右侧页面。
- 不新增完整顾客走动、排队或取货小剧场。
- 不让 UI 重新计算一套橱窗收益。
- 不让“集中收银”成为领取金币的经济门槛。

## 3. 已确认的体验方向

采用“销售脉冲型”作为主反馈方案：

- 单件商品自动成交时，在左侧对应商品格播放短促脉冲。
- 金额与主要原因就地出现，金币轨迹汇入橱窗顶部的本轮累计筹码。
- 三秒窗口内的同套装连续成交合并为连售。
- 玩家进入右侧“橱窗经营”并点击集中收银时，查看本轮总收入、最佳商品、最佳套装和冲突损失。
- 顾客只允许出现轻量反应气泡，不新增完整动画系统。

负面反馈采用“清晰但不惩罚”的强度：

- 冲突商品短暂轻震并显示红色关系线。
- 即时显示少赚金额或售速损失。
- 同时给出一条可执行的优化建议。
- 不播放强错误音，不阻止成交，不弹确认框。

## 4. 当前布局下的反馈分工

### 4.1 左侧橱窗

左侧始终是售卖主舞台，负责即时反馈：

- 哪个商品完成成交。
- 单件实际收入。
- 最主要的一条正向原因和一条负向原因。
- 套装连续成交与连售次数。
- 冲突关系、主要贡献关系和金币轨迹。
- 本轮累计收入与成交件数的紧凑筹码。

所有动效限制在橱窗区域内，不遮挡右侧工作台，不阻塞拖拽、旋转、移动或页面切换。

### 4.2 右侧工作台

采购、产出和研发制作页面保持现有结构。玩家停留在这些页面时，左侧仍正常播放自动成交反馈，不强迫切换页面。

“橱窗经营”负责聚合和解释：

- 自动营业状态。
- 本轮已入账金币、口碑和成交件数。
- 集中收银入口。
- 当前主要增益与减损。
- 最近成交明细。
- 本轮最佳商品、最佳套装和主要冲突。
- 下一轮最值得执行的一条调整建议。

## 5. 单次自动成交时序

普通成交在约 `0.9` 秒内完成，动效不阻断输入。

| 阶段 | 时间 | 表现 | 目的 |
| --- | ---: | --- | --- |
| 状态结算 | `0ms` | 先扣库存、入账金币与口碑、记录任务和成长 | 保证表现失败不影响经济正确性 |
| 商品脉冲 | `0-160ms` | 商品格轻弹、短暂金色描边 | 明确哪件商品成交 |
| 金额与原因 | `120-480ms` | 显示 `+金额`、一条主要增益和一条主要减损 | 解释这次成交结果 |
| 金币轨迹 | `300-750ms` | 金币从商品格飞向左侧累计筹码 | 建立商品与收入的空间联系 |
| 累计更新 | `500-900ms` | 本轮金额滚动增长，符合条件时更新连售 | 形成持续营业节奏 |

反馈优先级：

1. 套装成立或招牌商品成交。
2. 连续成交。
3. 普通成交。
4. 减损提示。

高优先级反馈可以压缩或覆盖低优先级反馈。减损必须清楚，但不能抢走爆单的主情绪。

## 6. 连续成交与降噪

- 同一时刻最多播放三个单件脉冲。
- 超过三个的其余成交合并为 `+N 件`。
- 同套装商品在三秒窗口内成交时合并为 `套装名 xN`。
- 连售只强化一次整体扫光和音高递进，不为每件商品重复弹窗。
- 即时原因最多显示一条主要正向原因和一条主要负向原因。
- 完整原因保留在右侧橱窗经营页与最近收银记录中。

## 7. 集中收银

### 7.1 经济语义

自动成交时金币已经真实入账。集中收银只消费“待查看收银汇总”，负责表现和复盘，不能再次增加金币或口碑。

玩家不点击集中收银、切换页面或退出游戏，都不会损失已经成交的收益。

按钮可以继续使用“集中收银”作为情绪文案，但必须同时标注“金币已入账”，避免玩家误以为不点击就拿不到收入。

### 7.2 页面表现

点击集中收银后：

- 不创建全屏弹窗。
- 左侧橱窗进行约 `1.2` 秒贡献回放：金色描边主要贡献商品与套装，红色描边主要损失商品。
- 右侧橱窗经营分区原位切换为本轮账单。
- 账单数字滚动显示基础收入、位置与相邻增益、套装与成长增益、冲突减损和最终收入。
- 显示最佳商品、最佳套装和一条下轮优化建议。
- 完成后右侧恢复经营概览，并清空已查看汇总。

## 8. 数据与组件边界

### 8.1 规则来源

`ShowcaseRuleService` 是 UI 反馈使用的唯一增益/减损来源。售价、售速、原因、套装与冲突信息必须来自真实规则计算结果，UI 不自行推导。

### 8.2 成交事件

`_sell_ready_showcase_slot()` 在真实状态更新完成后生成统一事件：

```gdscript
{
    "recipe_id": "sponge_cake",
    "anchor_slot": 23,
    "cells": [23, 24, 33, 34],
    "base_price": 40,
    "final_price": 48,
    "earned_coins": 48,
    "earned_reputation": 1,
    "price_multiplier": 1.2,
    "speed_multiplier": 1.18,
    "reasons": [],
    "groups": [],
    "timestamp": 0
}
```

事件同时提供给：

- 左侧即时反馈队列。
- 连售聚合器。
- 右侧待查看收银汇总。
- 最近收银记录。

### 8.3 组件职责

- `ShowcaseRuleService`：规则计算、原因和套装/冲突关系。
- `_sell_ready_showcase_slot()`：真实成交、一次性入账、生成反馈事件。
- `ShowcaseFeedbackDirector`：动画排队、优先级、连售合并和降噪。
- `showcase_board.tscn`：商品脉冲层、关系线层、浮字层、金币轨迹层和累计筹码。
- 右侧现有橱窗经营分区：汇总状态和集中收银回放。
- `main_view.gd`：绑定节点、转发事件、刷新页面与保存状态，不重新计算收益。

现有 `_settle_ready_showcase_goods()` 会继续处理到期商品并产生真实收入，不能直接作为新的“集中收银”按钮实现。实施时必须把“补处理到期销售”和“查看/清空收银汇总”拆成两个明确路径，后者只消费反馈汇总。

### 8.4 持久化

待查看收银汇总只保存聚合数据和少量最近成交记录，不保存动画状态。旧存档缺失这些字段时默认空汇总。

汇总数据不承担经济价值，因此载入、清空或丢失汇总都不能补发或扣除金币。

## 9. 异常与降级

- 动画节点缺失：跳过对应动画，成交、入账和记录保持成功。
- 商品节点已刷新或售罄：使用事件中的格子或橱窗中心播放聚合反馈。
- 规则原因缺失：显示普通基础售价成交，不显示空原因或未知错误。
- 同时成交过多：按三件上限压缩为聚合反馈。
- 玩家正在拖拽：不抢焦点、不阻塞输入，关系线和浮字可延后或缩短。
- 页面不在橱窗经营：继续累计汇总，不自动切页。
- 旧存档：初始化空汇总，不补发、不重复入账。
- 集中收银被重复点击：第一次消费汇总后，后续点击显示“暂无新的营业汇总”。

## 10. 验证与验收

### 10.1 逻辑验证

- 真实 `_process_showcase_sales()` 到 `_sell_ready_showcase_slot()` 路径只入账一次。
- 反馈事件的最终售价、金币和口碑与真实状态变化一致。
- 集中收银不会再次增加金币或口碑。
- 正向、负向原因和套装信息来自同一规则结果。
- 同时超过三件成交时能稳定压缩，且不会丢失汇总金额。
- 旧存档载入后汇总为空，不产生补发。

### 10.2 UI 验证

- `Main.tscn` 保持约 `63/37` 的左橱窗、右工作台结构。
- 采购、产出、研发制作、橱窗经营四个页面仍可正常切换。
- 左侧即时反馈不会改变右侧页面宽度或主界面尺寸。
- 橱窗经营页继续使用独立分区，不重新融合成一块长文本。
- 拖拽、移动、旋转和上架期间，售卖反馈不阻塞输入。
- 普通成交、套装连售、冲突减损和集中收银均有可识别的视觉差异。

## 11. 实施范围约束

- 稳定布局、反馈层和橱窗经营分区优先进入 `.tscn`。
- 脚本只负责状态绑定、事件队列、动画调度和格式化。
- 不为本功能重构采购、产出或研发制作页面。
- 不新增顾客寻路、排队或完整角色动画。
- 不改变已有橱窗规则数值；本设计只统一反馈与归因。
- 实施计划必须分阶段交付，先完成统一事件、即时脉冲和防重复入账，再增加连售与集中收银回放。
