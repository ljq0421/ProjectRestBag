# 橱窗利润、售速与顾客预算解耦设计

日期：2026-07-13
适用项目：`D:\Project\ProjectRest\project-rest`
状态：已完成方向讨论，待用户复核

## 1. 背景

当前橱窗规则会把相邻标签、套装、区域、主题、道具和商品成长等效果合并进商品最终售价；顾客购买时又直接拿该最终售价与固定预算比较。因此，本来标签匹配且买得起的商品，可能因为玩家摆出了正确组合、获得正向售价加成，反而变成“超预算”并失去成交。

示例：

- 商品基础售价为 20；
- 顾客预算为 20，且商品标签符合其偏好；
- 相邻组合提供售价 `+10%`；
- 当前结果为最终售价 22，顾客因超预算离店。

这会让“橱窗正向奖励”与“满足顾客需求”形成反向激励。

此外，现有显式顾客营业流程虽然仍计算 `speed_multiplier`，但顾客候选选择只比较标签命中数，购物时长也直接使用顾客的固定分钟数。橱窗的售速加成没有完整进入当前顾客购买路径。

## 2. 设计目标

1. 正向橱窗组合稳定奖励更高利润，不再制造预算淘汰。
2. 售速加成真正影响商品成交倾向与顾客购物时长。
3. 保留小份、礼盒、大份、试吃、新鲜度和晚间折扣的真实定价取舍。
4. 标签匹配始终先于售速；高售速不能让顾客购买不符合偏好的商品。
5. 今日需求预测与真实营业复用同一套报价、候选和时长规则。
6. 玩家能区分顾客支付、陈列经营收益与店铺总入账。
7. 规则由服务层统一计算，界面只负责展示，不复制经济公式。

## 3. 非目标

- 不调整顾客到店数量、到店时段或客群权重。
- 不调整现有顾客预算、配方基础售价或橱窗规则百分比。
- 不新增顾客类型、商品标签或橱窗组合规则。
- 不让售速直接生成额外顾客。
- 不为本次规则调整新增独立货币。
- 游戏仍在开发阶段，本设计不处理旧存档兼容、字段迁移或营业中途恢复。

## 4. 方案比较与结论

### 4.1 采用：顾客价与陈列经营收益分层

商品规格、新鲜度和晚间折扣决定顾客实际面对的价格；正向橱窗效果转为店铺额外经营收益。顾客只用顾客价与预算比较，店铺按顾客价加陈列收益入账。

优点：

- 正确陈列不会降低成交率；
- 礼盒、大份等主动定价仍有预算风险；
- 利润与售速都能作为清晰、可见的橱窗奖励；
- 能直接解释每笔收入来自商品还是布局。

### 4.2 未采用：同步提高顾客有效预算

橱窗售价提高多少，就按相同比例提高匹配顾客的支付意愿。该方案能维持成交，但会让顾客预算随布局动态变化，预测和反馈都较难理解。

### 4.3 未采用：最终售价按顾客预算封顶

先计算加成售价，再把成交价限制在顾客预算内。该方案不会丢单，但同一商品面对不同顾客的收入不稳定，玩家难以预测橱窗价值，也会削弱高预算客群的差异。

## 5. 价格与收入模型

### 5.1 三类倍率

`ShowcaseRuleService` 将现有综合结果拆成三类：

| 倍率 | 来源 | 作用 |
|---|---|---|
| `product_price_multiplier` | 小份、标准、礼盒、大份、试吃等规格 | 同时影响预算判断和店铺收入 |
| `display_profit_multiplier` | 相邻、套装、区域、冲突、主题、道具、商品陈列成长 | 正向部分增加经营收益；净负向部分降低顾客价与收入 |
| `speed_multiplier` | 规格与所有陈列售速效果 | 影响同等候选排序与购物时间 |

新鲜度和晚间折扣继续由商品新鲜度服务提供 `freshness_multiplier`，不混入陈列利润倍率。

### 5.2 结算公式

先计算不含陈列效果的原始报价：

```text
reference_price_raw = base_price
                    × product_price_multiplier
                    × freshness_multiplier
```

再计算顾客价和店铺总入账：

```text
customer_price = round(reference_price_raw × min(display_profit_multiplier, 1.0))
earned_coins   = round(reference_price_raw × display_profit_multiplier)
display_profit_coins = max(0, earned_coins - customer_price)
```

约束：

- 所有最终字段只取整一次；中间倍率保持浮点数。
- 顾客预算只与 `customer_price` 比较。
- `display_profit_multiplier > 1.0` 时，顾客价不被抬高，多出的部分进入 `display_profit_coins`。
- `display_profit_multiplier < 1.0` 时，顾客价和店铺收入一起降低，使引流位、冲突和折价布局仍有真实经济含义。
- `earned_coins` 不得小于 0。
- 售价与售速倍率继续使用服务层统一上下限，避免异常配置产生负数或无限增长。

### 5.3 示例

基础售价 20、顾客预算 20、标准规格、新鲜商品：

| 情况 | 顾客价 | 陈列收益 | 店铺入账 | 结果 |
|---|---:|---:|---:|---|
| 无橱窗加成 | 20 | 0 | 20 | 成交 |
| 正向陈列 `+10%` | 20 | 2 | 22 | 成交 |
| 礼盒规格 `+25%` | 25 | 0 | 25 | 超预算 |
| 净负向陈列 `-10%` | 18 | 0 | 18 | 成交 |
| 礼盒 `+25%` 且正向陈列 `+10%` | 25 | 3 | 28 | 仍因顾客价 25 超预算 |

## 6. 顾客候选与售速

### 6.1 候选资格

商品必须同时满足以下条件才能进入候选：

1. 至少命中顾客一个偏好标签；
2. `customer_price <= budget`；
3. 商品仍在橱窗上架；
4. 橱窗库存大于 0。

售速不能绕过标签、预算或库存条件。

### 6.2 候选排序

合格候选按以下顺序确定本次计划购买商品：

1. 命中偏好标签数量更多；
2. `speed_multiplier` 更高；
3. `customer_price` 更低；
4. 商品 ID 字典序更小，保证相同输入产生稳定结果。

售速只在偏好命中数量相同的商品之间发挥作用，不覆盖更强的顾客偏好。

### 6.3 购物时间

```text
effective_shopping_minutes = max(1.0, base_shopping_minutes / speed_multiplier)
```

- 购物时间保留小数，不能提前取整，否则小幅售速加成可能完全失效。
- 正向售速缩短当前顾客占用橱窗的时间，高峰期能更快处理排队，并降低临近打烊时来不及结算的风险。
- 负向售速延长购物时间。
- 售速不改变当天已经生成的顾客数量。

## 7. 顾客浏览快照

顾客开始浏览时建立仅限当前运行期使用的报价快照，包含：

- 计划商品 ID；
- 顾客价；
- 陈列收益；
- 总入账；
- 售速倍率；
- 实际购物时间；
- 完整加成与减益原因。

快照规则：

- 顾客进店时已有合适商品：锁定本次报价和原因；之后移动橱窗只影响下一位顾客。
- 进店时没有合适商品：使用基础购物时间；结算前重新检查一次当前橱窗，允许玩家临时补货或上架。
- 锁定商品被售罄或下架：结算时按当前橱窗寻找其他合适商品。
- 回退商品使用结算时的当前报价，但不追溯修改已经经过的购物时间。
- 营业结束、重新开始营业或退出当前运行时，直接清空浏览快照。

本设计不保存浏览快照，也不为旧运行数据提供迁移逻辑。

## 8. 运行时数据契约

成交或预览结果使用明确字段：

| 字段 | 含义 |
|---|---|
| `base_price` | 配方基础售价 |
| `customer_price` | 顾客实际支付并参与预算判断的价格 |
| `display_profit_coins` | 正向陈列产生的额外经营收益 |
| `earned_coins` | 本次实际增加的金币 |
| `speed_multiplier` | 本次锁定的售速倍率 |
| `shopping_duration_minutes` | 本次实际购物时间 |
| `reasons` | 陈列收益、折价与售速变化的来源 |

开发阶段直接移除该购买路径中含义模糊的 `final_price`，并更新所有运行时调用者、反馈和测试，不保留双轨字段。

营业收入、任务事件和营业报告统一使用 `earned_coins`；顾客预算、超预算原因和顾客卡统一使用 `customer_price`。

## 9. 玩家反馈

### 9.1 橱窗商品提示

```text
顾客价 20｜陈列收益 +2｜预计入账 22
售速 +10%｜来源：软糯甜口组合
```

净负向陈列使用“陈列折价”文案，并显示顾客价与入账同步下降。

### 9.2 当前顾客

顾客开始浏览后，当前顾客卡显示计划商品、预算、顾客价和预计完成时间。若当前没有计划商品，则显示正在寻找的偏好标签，不提前伪造成交。

### 9.3 成交反馈

```text
放学学生购买白糖米糕
支付 20｜陈列收益 +2｜入账 22
```

成交原因沿用服务层的完整 `reasons`，界面不自行推导倍率。

### 9.4 未成交反馈

超预算反馈只引用顾客价：

```text
心仪商品超出预算：顾客预算 20，最低顾客价 25
```

菜单不符、缺货和超预算继续保持互斥、可解释的结果分类。

### 9.5 营业总结

营业总结和经营账本分别显示：

- 顾客支付合计；
- 陈列经营收益合计；
- 总入账；
- 售速加成影响的成交商品与原因。

## 10. 模块边界

### 10.1 `ShowcaseRuleService`

- 输出商品定价倍率、陈列利润倍率和售速倍率。
- 继续负责相邻、套装、区域、冲突、主题、道具和成长原因。
- 提供统一的收入归因，不能再用顾客价反推陈列收益。

### 10.2 `CustomerVisitService`

- 成为商品报价、预算判断、候选排序、浏览计划和结算的唯一规则入口。
- 提供供实际营业与需求预测共同使用的纯预览函数。
- 结算时消费库存并把 `earned_coins` 加入店铺金币。

### 10.3 `CustomerDemandForecastService`

- 不复制候选与价格公式。
- 使用 `CustomerVisitService` 的同一计划与预览入口模拟剩余顾客。
- 预测结果必须包含顾客价、陈列收益、总入账和预计购物时间。

### 10.4 `GameState`

- 仅在当前运行期保存当前顾客浏览快照。
- 营业结束或重新开始时清空快照。
- 不新增存档字段和迁移代码。

### 10.5 `BusinessReportService`

- 分别累计顾客支付、陈列收益与总入账。
- 预算风险读取 `customer_price`，收入统计读取 `earned_coins`。

### 10.6 `main_view.gd` 与 UI 场景

- 协调顾客开始浏览、到期结算和界面刷新。
- 展示服务层返回的价格、收入、售速和原因。
- 不在界面层重新计算倍率或预算结果。

## 11. 异常与边界规则

- 高售速但零标签匹配：不进入候选。
- 标签匹配但顾客价超预算：返回 `over_budget`。
- 锁定商品缺货且存在其他合适商品：回退成交。
- 锁定商品缺货且没有替代商品：返回 `out_of_stock`。
- 没有任何标签匹配商品：返回 `menu_mismatch`。
- 没有可成交商品时，失败优先级固定为：存在预算内但缺货的匹配商品则返回 `out_of_stock`；否则存在匹配商品则返回 `over_budget`；完全没有标签匹配商品才返回 `menu_mismatch`。结果同时保存最低匹配顾客价供反馈使用。
- 浏览期间调整橱窗：不改变已有快照，只影响后续顾客；无计划商品和失效商品允许在结算时回退检查。
- 商品倍率配置缺失：商品倍率、陈列利润倍率和售速倍率分别回退到 `1.0`。
- 原始价格、最终顾客价和入账均不得为负数。

## 12. 验收标准

### 12.1 经济规则

1. 基础价 20、预算 20、陈列利润 `+10%`：成交，顾客支付 20，陈列收益 2，入账 22。
2. 基础价 20、礼盒 `+25%`、预算 20：返回超预算。
3. 净陈列效果 `-10%`：顾客价和入账均为 18。
4. 正向陈列加成不改变任何顾客的预算字段。
5. 结算增加金币的数值始终等于 `earned_coins`。

### 12.2 售速与候选

1. 售速 `1.25` 时，4 分钟基础购物时间变为 3.2 分钟。
2. 两款命中数相同的商品中，售速更高者优先成交。
3. 命中数不同的商品中，命中更多者优先，不被售速覆盖。
4. 高售速但零标签匹配的商品不会成交。
5. 售速变化不修改当天顾客总数。

### 12.3 快照与回退

1. 浏览期间移动商品不改变当前顾客锁定的价格、收益和售速。
2. 下一位顾客使用调整后的新布局。
3. 锁定商品缺货时正确回退到其他合适商品。
4. 无替代商品时返回正确的缺货、超预算或菜单不符结果。
5. 营业结束和重新开始后没有上一轮顾客快照残留。

### 12.4 预测与界面

1. 今日需求预测与实际营业对相同状态、顾客和橱窗得出相同商品、顾客价和结果。
2. 橱窗提示同时显示顾客价、陈列收益、预计入账和售速原因。
3. 成交反馈同时显示顾客支付、陈列收益和总入账。
4. 超预算反馈引用最低顾客价，不引用店铺总入账。
5. 营业总结分别汇总顾客支付、陈列收益和总入账。
