# 橱窗营业轮补完与 1920×1080 布局收敛设计

## 目标

在不重构整个经营框架的前提下，严格补齐 `2026-07-14-showcase-30-second-business-round.md` 中尚未达到验收标准的 Task 9–12 与 Task 14，并修复 1920×1080 基准页面内的组件溢出。

本轮完成后的唯一验收口径是：营业轮经济逻辑可确定性重放，挑战不再保留旧静态评分入口，营业信息能解释成交档位，所有主要页面和弹窗在 1920×1080 视口内可访问，计划要求的自动化回归全部通过。

## 范围

### 包含

- 商品角色由形状、标签、变体和成长共同决定。
- 基础、市场、布局与连锁收益通过同一纯计算管线重放归因。
- 特殊挑战使用完整且不可变的营业轮挑战快照。
- 调整阶段显示逐商品预计成交次数与跨档差距。
- 结算弹窗支持摘要和商品明细两层切换。
- 橱窗格子从 80×80 调整为 72×72，配方图标和角标同步缩放。
- 主页面、覆盖层和主要弹窗以 1920×1080 为硬边界完成布局验收。
- 更新陈旧的右侧经营页与 MVP 回归基线。

### 不包含

- 不拆分或重写整个 `main_view.gd`。
- 不改变现有甜品店主题、字体体系和主色板。
- 不改变 12 行×14 列棋盘、中心 6×6 初始开放区域或 30 秒标准营业时长。
- 不为低于 1920×1080 的分辨率重新设计完整响应式布局；现有 viewport 拉伸策略继续生效。
- 不增加新的长期玩法系统、商品类别或挑战货币。

## 一、商品角色快照

### 输入

每个已摆放商品在开轮前提供：

- 配方 ID、形状类别、标签；
- 当前变体 ID；
- 配方成长等级；
- 锚点和占用格；
- 本轮最终销售条款。

### 决策优先级

角色决策必须确定且可解释，优先级从高到低为：

1. `showcase_round_rules.json` 中明确列出的少量配方覆盖；
2. 变体覆盖；
3. 标签组合覆盖；
4. 成长达到配置阈值后的角色提升；
5. 形状模板基础角色。

没有匹配覆盖时使用形状模板角色。规则结果保存 `role`、`role_source`、`role_reason` 和有序目标列表，开轮后不再查询可变布局。

### 配置原则

- 具体映射保存在 `showcase_round_rules.json`，服务内只保留安全默认值。
- 同一商品只能得到一个主角色。
- 标签数组和目标数组排序后再参与判断，避免字典遍历顺序影响结果。
- 招牌配方覆盖保持少量、显式，不根据售价自动推断。

## 二、营业轮收益重放

### 单一计算入口

扩展 `ShowcaseRoundSaleService`，提供根据以下快照重放完整营业轮的纯计算入口：

- 初始批次库存；
- 商品销售条款；
- 营业轮时长；
- 按 `elapsed_ms` 排序的补货日志；
- 环境快照；
- 布局角色与连锁快照。

运行时成交与报告重放必须共享销售周期推进、批次优先级、事件排序和连锁解析规则，不复制近似公式。

### 三条重放

报告生成时执行三条确定性重放：

1. 基础重放：关闭环境、布局加成和连锁；
2. 市场重放：仅应用环境；
3. 完整重放：应用环境、布局和连锁。

归因定义：

- `base_income = 基础重放收入`；
- `market_income = 市场重放收入 - 基础重放收入`；
- `layout_extra_income = 完整正常成交收入 - 市场重放收入`；
- `clearance_income = 5 折清仓 + 1 折强制清仓`；
- `total_coins = 完整正常成交收入 + clearance_income`。

每次重放使用相同初始库存与真实补货时间。报告若不能对账，拒绝保存该报告并显示明确开发错误，不静默修正差额。

## 三、特殊挑战收口

### 唯一入口

删除 `ShowcaseChallengeService` 中旧的 `CHALLENGE_DEFINITIONS`、`score_showcase()` 和 `evaluate_challenges()` 静态布局评分语义。营业轮挑战模板成为唯一挑战来源。

### 挑战快照

接受挑战前展示并保存：

- ID、版本、标题和说明；
- 时长；
- 布局、商品、标签或变体限制；
- 固定环境或环境覆盖；
- 目标指标与目标值；
- 保证金、成功奖励；
- 当前等级下解析后的可用对象列表。

挑战接受时验证其引用对象均已解锁。接受后快照不可重抽；失败只损失已展示保证金，不回扣本轮营业收入。

## 四、营业信息和结算层级

### 调整阶段商品信息

每件已摆放商品显示：

- 最终销售周期；
- 30 秒内预计完整成交次数；
- 当前售速距离多完成一次成交还差多少秒；
- 当前全价库存和 8 折留售库存；
- “预计以库存持续充足为前提”的固定说明。

预计次数只用于预览，不生成假想成交或缺货损失。

### 营业阶段商品信息

继续显示剩余营业时间、热度、锁定环境、当前周期进度、批次库存和待补货原因。营业中只允许同款补货，不允许移动、旋转或切换变体。

### 结算弹窗

弹窗使用场景中固定声明的切换控件：

- 摘要层：总金币、基础、市场、布局、清仓、成交数、最高贡献；
- 商品明细层：逐商品成交数、全价/8 折次数、贡献、补货、触发规则、角色、连锁和跨档差距；
- 余货处理区始终可达，不因切换明细而丢失选择状态。

未完成全部余货选择时确认按钮保持禁用，并显示缺少选择的商品。

## 五、1920×1080 布局

### 主棋盘

- 单格固定为 72×72；
- 棋盘固定为 1008×864；
- `ShowcaseSlot`、运行时 `SHOWCASE_CELL_SIZE` 和相关场景最小尺寸使用同一常量口径；
- 配方分片仍使用原始图集区域，`TextureRect` 在 72×72 格内缩放显示，避免重新生成整套资源；
- 状态角标最大宽度从 58 缩至 52，高度从 20 缩至 18，字号从 9 缩至 8；
- 图标、预览色块和关系轮廓继续忽略鼠标输入。

### 主页面空间分配

- 左侧棋盘区域以完整显示 1008×864 和营业控制条为最低要求；
- 右侧工作台保留不小于 720 像素可用宽度；
- 顶部栏、页面主体和状态栏的总高度不得超过 1080；
- 右侧长页面使用自身 `ScrollContainer`，不通过继续增加根节点最小高度解决；
- 顶部按钮保持单行，必要时优先压缩统计标签最小宽度，不缩小交互按钮至不可读。

### 覆盖层和弹窗

- 全局覆盖层不得使用超过锚点实际尺寸的硬编码最小高度；
- 结算、自动化报告、补货、小票等主要弹窗均需满足 `global_rect` 位于 1920×1080 内；
- 弹窗内容超长时由内部滚动容器承载；
- 不使用裁切来隐藏必要操作按钮。

### 视觉约束

继续使用现有 `Neighborhood Dessert` 主题、圆角面板、甜品色板和既有字体层级。此次视觉调整只改变密度和信息层级；标志性元素仍是左侧完整橱窗棋盘及其营业状态条。

## 六、测试与验收

### 测试驱动顺序

1. 为角色覆盖、报告三重重放、挑战快照和旧入口删除分别增加失败自检；
2. 为调整阶段预估、结算切换和旧文案清理增加失败自检；
3. 为 1920×1080 主场景、覆盖层和主要弹窗增加几何失败自检；
4. 修改最少实现使聚焦测试通过；
5. 更新右侧经营页和 MVP 的陈旧断言，使其验证当前项目真相；
6. 运行营业轮聚焦套件、UI 套件、完整 MVP 自检和 `git diff --check`。

### 1920×1080 几何断言

自检实例化 `Main.tscn` 并将根视口设为 1920×1080，至少断言：

- `Root`、`TopBar`、`Body`、`StatusBar` 全部位于视口内；
- 左右主面板不相互覆盖；
- 168 个橱窗格均为 72×72，最右和最下格不越界；
- 右侧各页面可以滚动到最后一个操作控件；
- 全局覆盖层和主要弹窗的确认/关闭按钮在视口内可见。

### 完成门槛

- Task 9–13 的聚焦测试全部通过；
- `right_console_experience_self_check.gd` 通过；
- `mvp_self_check.gd` 通过，且不通过删除有效业务断言来获得绿灯；
- 新增 1920×1080 几何自检通过；
- 旧自动售卖、旧静态挑战和旧绝对销售时间扫描均无匹配；
- `git diff --check` 通过；
- 完成一次调整、补货、标准轮、营业中补货、结算、余货选择和下一轮的实际交互路径验收。

## 七、失败处理

- 无法生成合法角色或挑战快照时禁止开轮，并给出具体配置错误。
- 报告重放不能对账时不发放第二次金币，也不覆盖原始成交记录。
- 1920×1080 几何自检发现溢出时，以修正容器、滚动和最小尺寸为主，不隐藏控件。
- 所有幂等入口继续使用轮 ID、结算 ID、挑战实例 ID 和成交事件 ID 防止重复执行。
