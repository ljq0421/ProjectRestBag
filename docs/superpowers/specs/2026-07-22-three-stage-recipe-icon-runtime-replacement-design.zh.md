# Rest New 三阶段配方图标渐进替换设计

## 目标

将 `resources/ui/icons_v1` 中的新画风配方图标按成长阶段接入运行时，并允许按单个配方或小批次逐步替换。已经替换的配方随 `mastery_level` 显示试作品、人气款或招牌款图标；尚未替换或缺少阶段图的配方继续显示现有基础图，不出现空白。

本批原始素材使用以下约定：

- `<recipe_id>_1.png`：试作品，`mastery_level = 0`；
- `<recipe_id>_2.png`：人气款，`mastery_level = 1`；
- `<recipe_id>_3.png`：招牌款，`mastery_level = 2`。

## 范围

本次接入以下运行时表面：

1. 图鉴卡片；
2. 库存配方格；
3. 制作和材料操作行；
4. 配方研发成功结果。

橱窗图标不在本次范围内。`resources/recipe_icons_showcase` 依赖形状、上架变体、旋转角度和切片 manifest，不能由三张方形阶段图直接替换。

## 方案选择

采用“原始素材、标准阶段资源、界面派生资源”三层结构。

没有采用让界面直接加载 `resources/ui/icons_v1` 的方案，因为原图为 1024×1024，文件名也不符合现有运行时约定。没有只覆盖 `<recipe_id>.png`，因为那样只能更换固定画风，无法表达配方成长阶段。

三层结构允许只安装指定配方，并通过基础图回退保护尚未完成的批次。

## 资源结构

### 原始素材

`resources/ui/icons_v1` 保留生成出的 1024×1024 RGBA PNG，不由运行时直接加载。

### 标准阶段资源

转换脚本将原图缩放为 512×512，并写入：

```text
resources/recipe_icons/<recipe_id>.png
resources/recipe_icons/<recipe_id>_popular.png
resources/recipe_icons/<recipe_id>_signature.png
```

其中无后缀文件表示试作品。该命名与项目已经存在的 `_popular`、`_signature` 约定一致。

### 界面派生资源

同一转换流程生成：

```text
resources/recipe_icons_catalog/<recipe_id>[阶段后缀].png      # 132×132
resources/recipe_icons_inventory/<recipe_id>[阶段后缀].png    # 80×80
resources/recipe_icons_action/<recipe_id>[阶段后缀].png       # 32×32
```

转换只覆盖命令中明确指定的配方，不清空或重新生成整个目标目录。PNG 保持 RGBA 和透明通道，缩放使用 Lanczos。

## 运行时解析

新增一个只负责配方图标路径与纹理加载的服务。调用方提供：

- `recipe_id`；
- `mastery_level`；
- 表面类型：`base`、`catalog`、`inventory` 或 `action`。

阶段后缀映射为：

```text
0 -> ""
1 -> "_popular"
2 -> "_signature"
```

解析按以下顺序回退：

1. 当前表面的目标阶段图；
2. 当前表面的试作品图；
3. `resources/recipe_icons` 中的目标阶段图；
4. `resources/recipe_icons/<recipe_id>.png`；
5. `null`。

服务只读取资源，不修改成长状态，也不持有 `GameState`。页面继续从 `GameState.get_recipe_growth(recipe_id)` 获取 `mastery_level`，因此资源选择和游戏状态保持单向依赖。

## 各表面行为

### 图鉴

图鉴是首个试点表面。已解锁卡片根据当前成长阶段加载对应图标，并保留现有阶段徽章、名作装饰、tooltip 和锁定逻辑。空白格与未解锁格不加载图标。

### 库存

配方库存格根据当前成长阶段加载 `inventory` 派生图。原料库存图标逻辑不变，上架变体和拖拽形状逻辑不变。

### 制作和材料操作行

配方类型材料根据当前成长阶段加载 `action` 派生图；原料仍然从 `resources/ingredient_icons` 加载。图标解析不能改变材料判断、制作可用性或按钮状态。

### 研发结果

新解锁配方通常处于试作品阶段。研发成功结果仍通过统一服务加载 `base` 表面；若状态中已经存在更高阶段，则显示对应阶段图。

## 渐进发布顺序

1. 用 `rice_milk_drink` 生成三阶段标准资源和派生资源；
2. 接入图鉴并验证 `mastery_level = 0/1/2` 的切换与缺图回退；
3. 接入库存；
4. 接入制作和材料操作行；
5. 接入研发结果；
6. 安装 `icons_v1` 中剩余九个配方；
7. 完成十个配方的资源完整性与界面回归检查。

每一步都保留回退逻辑，因此中途停止时未处理配方仍使用旧资源。

## 转换工具

新增独立批次转换工具，不直接复用当前会扫描全部配方或不理解阶段后缀的三个旧生成器。工具应支持：

```text
--source-dir resources/ui/icons_v1
--recipe-id rice_milk_drink
--recipe-id egg_milk_custard
```

工具先验证指定配方的 `_1/_2/_3` 三张输入均存在、尺寸一致且可转换为 RGBA，再写入输出。任一输入无效时，该次调用不得发布部分输出。

工具不删除任何非目标文件，不处理 `.import` 文件；Godot 负责重新导入变更后的 PNG。

## 刷新与缓存

图标服务可以在一次刷新内使用 Godot 的资源加载缓存，但不维护独立的永久缓存。页面现有刷新路径重新解析当前阶段，所以晋级并刷新页面后会立即显示新图，不需要重启游戏。

## 测试与验收

### 自动检查

1. 转换工具测试：映射、尺寸、透明通道、限定配方写入和失败时不产生部分输出；
2. 图标服务测试：三个阶段、四种表面、目标阶段缺失回退、所有资源缺失返回 `null`；
3. 图鉴测试：三个阶段选择正确纹理，锁定与空白格行为不变；
4. 库存和操作行测试：配方使用阶段图，原料图标路径不变；
5. 研发结果测试：通过统一服务显示正确阶段图；
6. 资源审计：十个配方在标准目录和三个派生目录中均有三阶段文件。

Godot 头less测试必须带可写的 `--log-file`。

### 可视验收

至少检查一个配方在图鉴 132×132、库存 80×80、操作行 32×32 和研发结果 128×128 中的透明边缘、主体占比与可识别性。再检查十个配方三阶段没有文件错配。

## 工作区保护

当前工作树包含与本功能无关的未提交界面、结算和配方验收导入改动。实施只添加图标服务、转换工具和针对性测试，并对 `scripts/main_view.gd` 做局部修改；不得还原、重排或提交其他未完成改动。

设计文档提交只包含本文。后续实现提交应只暂存本功能明确拥有的文件和行。
