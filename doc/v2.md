# 邻街甜品店 Godot 原型策划案

版本：0.1  
日期：2026-07-03  
目标项目：D:\Project\ProjectRest（Godot，项目名 project-rest）  
参考方向：《洋果子店rose2》的配方发现与轻经营节奏  

## 1. 项目定位

《邻街甜品店》是一款 PC 单机甜品店经营原型。玩家经营一家现代社区甜品店，通过采购食材、研发配方、制作甜品、上架售卖、积累口碑来升级店铺。

本原型借鉴《洋果子店rose2》中“食材 + 工法 = 新品发现”的核心乐趣，但题材、配方、数值、界面和内容均做原创设计。游戏包装重点不是传统图鉴收集，而是“社区顾客反馈推动新品研发”：玩家发现新品后，会用新品满足不同顾客偏好，从而获得金币和口碑。

## 2. 原型目标

本阶段目标是验证核心循环是否成立，而不是制作完整商业版内容。

必须实现：

- 约 20 个食材。
- 18 个甜品配方。
- 4 类制作设备。
- 1 个店铺主界面。
- 1 条店铺升级线。
- 可反复进行的“采购 -> 研发 -> 生产 -> 上架 -> 营业 -> 升级”循环。
- 本地存档。

暂不实现：

- 员工系统。
- 装修系统。
- 外卖平台。
- 限时活动。
- 多店铺。
- 完整剧情。
- 复杂烹饪小游戏。

## 3. 目标体验

玩家每 5-10 分钟应能完成一次明显的经营推进：

- 解锁 1 个新甜品。
- 补齐一类顾客偏好。
- 升级店铺或接近升级目标。
- 通过失败试做获得有用线索。

体验基调：

- 轻量、清晰、节奏快。
- 失败不惩罚过重，失败试做会给线索。
- 经营反馈要直接，玩家能看见新品对销量和口碑的影响。
- UI 以 PC 鼠标操作为主，减少多层弹窗和深菜单。

## 4. 核心循环

1. 采购：玩家用金币购买基础食材。店铺升级后解锁高级食材。
2. 研发：玩家选择 2-3 个食材和 1 个设备进行试做。
3. 解锁：组合命中隐藏配方后，甜品加入图鉴；未命中则返回配方线索。
4. 生产：玩家选择已解锁甜品，消耗食材制作成品。
5. 上架：玩家把成品放入橱窗槽位。
6. 营业：顾客根据价格和口味标签购买橱窗甜品。
7. 结算：获得金币、口碑和评价日志。
8. 升级：玩家用金币和口碑提升店铺等级，解锁更多内容。

## 9. 研发系统

### 9.1 操作

研发界面中，玩家选择：

- 1 个设备。
- 2-3 个食材或中间成品。
- 点击“试做”。

### 9.2 成功

如果组合命中配方：

- 解锁该配方。
- 首次解锁奖励少量口碑。
- 展示新品卡片：名称、售价、标签、说明。
- 消耗 1 组所选材料。

### 9.3 失败

如果未命中配方：

- 消耗所选材料的一半价格等价成本，简化为每个食材库存 -1。
- 返回一条线索。

线索优先级：

1. 设备错误：提示“这个组合也许不适合当前设备。”
2. 缺少关键材料：提示“味道接近了，但还缺少某种基底/乳制/水果/风味。”
3. 等级不足：提示“店铺经验还不足以稳定制作这种新品。”
4. 完全无关：提示“这次试做没有形成稳定商品。”

## 10. 生产系统

生产界面展示已解锁配方。玩家选择配方后点击制作：

- 检查食材库存。
- 消耗配方材料。
- 增加成品库存，数量等于配方份数。
- 获得一条生产日志。

原型不做真实时间等待，采用即时生产。后续商业版可扩展为队列和设备效率。

## 11. 橱窗与营业系统

### 11.1 橱窗

橱窗槽位用于决定营业时可售卖商品。

- 等级 1：3 个槽位。
- 等级 2：4 个槽位。
- 等级 4：5 个槽位。

每个槽位选择一种成品。售卖时从对应成品库存扣除。

### 11.2 顾客

顾客由系统按店铺等级生成。每个顾客有：

- 名称。
- 预算。
- 1-2 个偏好标签。
- 容忍价格。

顾客示例：

| 类型 | 偏好 | 预算 | 解锁等级 |
| --- | --- | ---: | ---: |
| 放学学生 | 甜, 低价 | 20 | 1 |
| 加班白领 | 苦甜, 浓郁 | 35 | 2 |
| 亲子家庭 | 果香, 经典 | 40 | 2 |
| 健身居民 | 清爽, 低负担 | 35 | 3 |
| 老街熟客 | 经典, 甜 | 30 | 3 |
| 探店博主 | 招牌, 稀有 | 50 | 5 |

### 11.3 购买判定

每个顾客从橱窗商品中选择得分最高的商品：

```
商品得分 = 标签匹配数 * 10 + 店铺等级加成 - 价格超预算惩罚
```

规则：

- 得分大于 0 且商品有库存：购买。
- 购买后获得金币 = 商品售价。
- 口碑增加 = 1 + 标签匹配数。
- 没有合适商品：顾客离开，记录一条反馈。

### 11.4 营业结算

点击“开始营业”后即时模拟一轮顾客：

- 等级 1：6 人。
- 等级 2：8 人。
- 等级 3：10 人。
- 等级 4：12 人。
- 等级 5：14 人。

结算展示：

- 售出件数。
- 获得金币。
- 获得口碑。
- 缺货次数。
- 未满足偏好列表。

## 13. 主界面设计

使用单主界面承载全部流程，避免原型期多场景复杂度。

### 13.1 布局

- 顶部资源栏：金币、口碑、等级、当日顾客数。
- 左侧导航：采购、研发、生产、橱窗、图鉴、升级。
- 中间工作区：当前标签页主要操作。
- 右侧反馈栏：顾客反馈、研发线索、营业结算日志。
- 底部状态条：当前提示、错误反馈、存档状态。

### 13.2 交互原则

- 按钮不可用时显示原因，例如“库存不足”“等级不足”“未解锁设备”。
- 研发和生产的消耗在点击前可见。
- 营业结算直接展示结果，不让玩家猜数值变化。
- 图鉴中未解锁配方显示线索，不显示完整答案。

## 14. Godot 技术设计

### 14.1 场景结构

建议采用一个主场景：

```
Main.tscn
└── MainView (Control)
    ├── TopBar
    ├── NavigationTabs
    ├── ContentPanel
    ├── FeedbackPanel
    └── StatusBar
```

原型以 UI 为主，不需要角色移动场景。

### 14.2 脚本模块

| 脚本 | 职责 |
| --- | --- |
| game_state.gd | 保存金币、口碑、等级、库存、成品、橱窗、已解锁配方 |
| catalog.gd | 定义食材、设备、配方、顾客、升级表 |
| recipe_book.gd | 研发匹配、线索生成、配方解锁 |
| shop_simulation.gd | 顾客生成、购买判定、营业结算 |
| save_system.gd | JSON 存档读写 |
| main_view.gd | UI 渲染、按钮事件、标签切换 |

### 14.3 数据组织

第一版可把数据写在 `catalog.gd` 的字典中，降低资源文件维护成本。实现稳定后再迁移到 JSON 或 Resource。

推荐结构：

```
res://scenes/Main.tscn
res://scripts/game_state.gd
res://scripts/catalog.gd
res://scripts/recipe_book.gd
res://scripts/shop_simulation.gd
res://scripts/save_system.gd
res://scripts/main_view.gd
```

### 14.4 存档

存档路径：

```
user://neighbor_dessert_save.json
```

保存字段：

- coins
- reputation
- shop_level
- ingredient_inventory
- product_inventory
- unlocked_recipes
- display_slots
- discovered_hints

## 15. 测试与验收

### 15.1 功能验收

- 能采购基础食材。
- 能用正确组合解锁至少 18 个配方。
- 错误组合能返回线索。
- 能生产已解锁甜品。
- 能把成品放入橱窗。
- 营业能出售匹配商品并获得金币与口碑。
- 缺货或不匹配会生成顾客反馈。
- 满足条件后能升级店铺。
- 等级会解锁新食材、设备或槽位。
- 退出重进后能恢复存档。

### 15.2 原型完成标准

当玩家能从等级 1 经营到等级 5，并解锁至少 15/18 个配方时，原型达成本阶段目标。

### 15.3 风险

- 如果 UI 信息过多，单主界面会拥挤。应优先保证采购、研发、生产、橱窗四个核心标签清晰。
- 如果配方线索太弱，玩家会随机试错。每次失败必须给出方向性反馈。
- 如果营业结算太自动，玩家会缺少经营掌控感。橱窗选择和标签匹配必须是销量差异的主要原因。
- 如果升级成本过高，原型节奏会拖慢。第一版数值应偏宽松。

## 16. 后续扩展方向

完成原型后，可逐步增加：

- 顾客常客系统。
- 社区事件，例如雨天、节日、学校放假。
- 员工与生产队列。
- 装修影响客流。
- 更多复合配方。
- 食材品质。
- 每周目标和经营报表。
