# ProjectRest New Markdown 配方验收解锁设计

**日期：** 2026-07-22

**项目：** `D:\Project\ProjectRest\project-rest-new`

**状态：** 已批准，待实施计划

## 1. 目标

提供一个仅在调试版本可用的快捷入口。按下 `Ctrl + Alt + U` 后，游戏读取固定 Markdown 文件，提取其中列出的配方 ID，将这些配方及其必要前置条件写入当前开发存档，并刷新正常游戏页面。

导入完成后，玩家应当沿用真实游戏链路：

1. 在图鉴中看到这些配方处于已解锁状态；
2. 在制作页面看到并正常制作这些配方；
3. 制作完成后，成品进入现有 `product_inventory`；
4. 从库存使用现有拖拽数据和上架校验将成品放入橱窗。

本功能不是独立图标预览器，不创建专用验收界面，也不伪造人气款或招牌款成长状态。图标应当通过图鉴、制作、库存和橱窗等真实页面接受检查。

## 2. 入口与清单

### 2.1 调试入口

- 快捷键固定为 `Ctrl + Alt + U`，避开 Godot 编辑器用于停止运行项目的 `F8`。
- 仅当 `OS.is_debug_build()` 为真时响应；发行版本不暴露该入口。
- 固定读取 `res://doc/recipe_icon_preview_manifest.md`。
- 重复执行必须幂等：已经满足的等级、功能、权限、设备和配方不重复写入。

### 2.2 Markdown 解析

解析器接受三类明确标记：

- 整行只有 `<recipe_id>` 的裸 ID，允许行首和行尾空白；
- `resources/recipe_icons/<recipe_id>.png` 形式的配方图标路径；
- Markdown 标题末尾括号中的 `<recipe_id>`。

裸 ID 必须占据整行；不接受列表符号，不扫描正文或行内代码中的蛇形单词。对于带 `_popular` 或 `_signature` 后缀的成长图标文件名，先移除阶段后缀，再校验基础配方 ID。所有候选值必须与 `Catalog.get_recipes()` 交叉校验，避免把原料、设备或提示词代码块中的其他蛇形 ID 误判为配方。

合法 ID 按第一次出现在 Markdown 中的顺序保留并去重。非法候选值不进入状态变更计划，但应出现在结果报告中。若文件不存在、无法读取或没有任何合法配方，整个操作直接终止且不修改状态。

## 3. 架构

### 3.1 导入服务

新增一个职责单一的调试导入服务，负责：

1. 读取并解析 Markdown；
2. 根据当前 Catalog 构建依赖闭包；
3. 生成不修改状态的导入计划；
4. 对传入的 `GameState` 应用计划；
5. 返回结构化报告，供主界面显示结果和测试断言。

该服务不负责保存文件、切换页面或操作具体 UI 节点。主界面只负责监听 `Ctrl + Alt + U`、调用服务、保存、回滚、刷新和显示状态摘要。

### 3.2 依赖闭包

导入计划从 Markdown 中的目标配方开始，递归补齐：

- 目标配方本身；
- 若某个材料 ID 同时属于配方，则补齐该前置配方及其依赖；
- 每个配方所需的制作设备；
- 加工原料对应的加工配方、加工设备和加工输入；
- 加工产物的加工权限；仅当 Catalog 为该产物明确声明可解锁采购条件时，才同步补齐采购权限；
- 原料、加工配方、前置配方和生产来源所需的最低店铺等级。

设备统一通过显式设备解锁满足，不使用设备的事件门槛或 `999` 哨兵等级抬高店铺等级。农场、林场、牧场、水塘及普通采购项没有独立权限账本的部分，继续依靠计算出的店铺等级按正常规则开放。

依赖计算只开放取得和制作所需的权限，不赠送原料、种子、成品、工具、金币、经验或成长次数。

### 3.3 核心功能链

为保证真实页面和拖拽上架可用，导入器按 `CoreFeatureUnlockService.ORDER` 依次调用现有解锁接口，直到并包含 `LIST`：

`采购 → 产出 → 库存 → 研发 → 制作 → 图鉴 → 上架`

不解锁经营规则、橱窗调整、营业、橱窗经营、任务或星辉。解锁核心功能不等于完成教程；不得写入教程完成状态、任务完成状态或奖励领取状态。

## 4. 状态应用顺序

主界面收到合法导入计划后按以下顺序执行：

1. 保存会受本次操作影响的状态快照；
2. 将店铺等级提升到依赖闭包要求的最高等级，只升不降；
3. 按既有顺序解锁核心功能直到 `LIST`；
4. 解锁所需设备；
5. 解锁所需加工权限；仅对 Catalog 明确允许解锁采购的加工产物补齐采购权限；
6. 使用 `state.add_recipe(recipe_id, false)` 解锁目标配方和必要的前置配方；
7. 通过现有 `_save_game()` 统一保存一次；
8. 刷新核心功能入口、图鉴、制作页、库存、橱窗和当前页面；
9. 在状态栏显示导入摘要。

必须先提升等级，再调用 `add_recipe()`，因为现有接口会拒绝高于当前店铺等级的配方。`notify=false` 用于避免批量解锁通知。导入器不调用 `RecipeBook.research()`、`TutorialProgress.on_recipe_unlocked()` 或 `record_task_event()`，因此不伪造研发、教程或任务事件。

## 5. 正常游戏链路

导入成功后不创建旁路制作或旁路上架逻辑：

- 图鉴继续依据 `state.is_recipe_unlocked()` 渲染卡片；
- 制作页继续依据解锁配方、设备与实际库存决定按钮状态；
- 制作仍通过 `RecipeBook.make_product()` 和现有制作队列进行；
- 成品仍由队列完成逻辑写入 `product_inventory`；
- 库存仍创建现有 `inventory_product` 拖拽数据；
- 上架仍通过 `LIST` 权限、占格、库存和橱窗校验。

因此，导入后若实际原料库存不足，制作按钮显示缺料是正确行为。验收者需要通过正常采购、生产或加工取得材料，或在自动化测试夹具中显式补充材料。

## 6. 图标资源审计

导入报告同时检查目标配方在真实页面使用的资源是否存在，包括：

- 基础配方图标 `resources/recipe_icons/<recipe_id>.png`；
- 图鉴图标 `resources/recipe_icons_catalog/<recipe_id>.png`；
- 制作操作图标 `resources/recipe_icons_action/<recipe_id>.png`；
- 库存图标 `resources/recipe_icons_inventory/<recipe_id>.png`；
- 橱窗标准变体在 `showcase_icon_manifest.json` 中的布局与贴图条目。

资源缺失不阻止解锁或保存，因为正常页面出现空白、缺图、裁切或布局错误正是本工具需要暴露的问题。状态摘要应报告缺失数量，并将详细配方 ID、页面用途和资源路径写入调试输出。

## 7. 原子性与错误处理

在应用计划前，主界面至少快照以下状态：

- `level`；
- `core_feature_unlocks`；
- `unlocked_devices` 与 `device_growth`；
- `ingredient_purchase_unlocks`；
- `ingredient_process_unlocks`；
- `unlocked_recipes`；
- 由现有解锁接口追加的反馈日志。

若保存失败，立即恢复快照并刷新页面，使内存状态与磁盘存档保持一致。

其他错误策略：

- Markdown 文件缺失或不可读：不修改状态；
- 合法配方为零：不修改状态；
- 合法与非法 ID 混合：导入合法项，并在摘要中列出忽略项；
- 依赖引用不存在：该目标配方标记为失败，不应用不完整依赖；其他依赖完整的目标配方仍可导入；
- 重复 ID 或已解锁项：不重复处理；
- 正在制作、营业或结算：不改动运行中队列、营业状态或结算数据，只补充解锁状态并刷新列表。

## 8. 玩家可见反馈

成功后状态栏显示一条汇总信息，至少包含：

- Markdown 中识别的合法目标配方数；
- 新增配方数与已经解锁数；
- 自动补齐的前置配方、设备、原料权限数量；
- 店铺等级的原值和新值；
- 忽略的非法 ID 数；
- 缺失图标资源数；
- 存档是否成功。

不得为每个配方排队解锁通知，也不得弹出研发成功对话框。

## 9. 验证标准

至少覆盖以下自动化验证：

1. 从现有配方图标 Markdown 中提取合法配方 ID，排除材料和设备 ID，并按首次出现顺序去重。
2. `_popular`、`_signature` 文件名能够正确还原基础配方 ID。
3. 高等级目标配方能补齐店铺等级、制作设备、加工配方、加工设备和原料权限；没有采购解锁条件的加工产物不得伪造采购权限。
4. 核心功能只开放到 `LIST`，不开放后续经营、任务和星辉功能。
5. 导入不触发研发事件、教程进度、任务奖励、通知或配方成长。
6. 导入成功后保存并重新加载，等级、权限、设备和配方解锁仍然存在。
7. 图鉴和制作页面立即显示目标配方为已解锁。
8. 测试夹具补充真实材料后，配方能通过现有制作队列完成并进入 `product_inventory`。
9. 成品库存格生成现有拖拽数据，并能通过现有上架校验放入橱窗。
10. 图标资源缺失会进入报告但不阻止有效配方解锁。
11. 文件缺失、零合法配方和保存失败时不会留下部分状态变更。
12. 连续执行两次导入，第二次不重复改变状态或追加重复解锁日志。
13. Godot 项目能够无解析错误启动或退出，且 `git diff --check` 通过。

Godot 无头测试必须从项目根目录运行，并为每次命令传入写入临时目录或工作区的显式 `--log-file`，避免沙箱访问默认 `user://logs` 时崩溃。

## 10. 实施边界

本次不修改：

- 正常研发成功率、材料消耗或研究提示；
- 正常制作时间、产量或库存规则；
- 橱窗占格、变体、拖拽或营业规则；
- 配方成长、人气款、招牌款或名作状态；
- 教程完成、任务完成或奖励领取记录；
- Markdown 以外的其他配方解锁状态。

当前工作区已有其他未提交代码、场景、配置和素材改动。实施时必须保留这些改动，并将本功能限制在 `project-rest-new`。
