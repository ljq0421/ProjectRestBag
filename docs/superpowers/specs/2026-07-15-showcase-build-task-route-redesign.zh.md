# 橱窗构筑任务路线重设计

日期：2026-07-15  
状态：设计已确认；2026-07-15 修订 Lv.0 销售条款节点
适用项目：`D:\Project\ProjectRest\project-rest-new`

## 1. 背景与问题

`project-rest-new` 的核心体验已经转为短回合橱窗构筑：

> 调整布局 → 补货 → 确认环境 → 开始营业 → 30 秒自动售卖与轮内补货 → 本轮结算 → 处理余货 → 再次调整

现有任务路线仍主要围绕采集次数、指定设备制作、指定顾客购买、研发次数和累计经营数值展开。真正考查布局、售速、补货、余货处理和连锁收益的任务出现过晚，导致任务给出的目标与玩家实际反复操作的核心循环不一致。

当前后期任务还存在定义漂移：任务引用的挑战 ID 与实际可选挑战模板不一致，挑战结算也没有通过统一路径推进任务。继续在旧路线末端追加任务只会扩大两套目标体系之间的分裂。

本设计重建任务内容、阶段结构和判定来源，但保留现有任务面板、奖励领取和通用任务状态能力。

## 2. 设计目标

1. Lv.0–Lv.2 用强引导让玩家逐步掌握完整营业闭环和基础构筑规则。
2. Lv.3 起，主线任务全面转为橱窗构筑挑战，不再以采集、制作或研发次数作为主线完成条件。
3. Lv.6 起不再编写逐级固定主线，改用可重复经营合同、主题赛事和门店评级提供长期目标。
4. 所有营业类任务、挑战评级、结算说明和历史报告读取同一份营业轮报告。
5. 每个目标在营业前可理解、营业中可追踪、结算后可解释。
6. 任务不要求玩家解锁某个指定配方；优先使用当前已开放的标签、商品角色、格数和营业指标出题。
7. 采集、生产、研发和自动化保留为资源支线，为橱窗构筑提供补给，但不主导成长方向。

## 3. 非目标

- 不把游戏重做为完整赛程制 Roguelite，不引入胜场或失败次数结束整局的结构。
- 不改变标准营业轮固定 30 秒、各商品独立待售时间和明确结算边界。
- 不把顾客关系、NPC 好感或指定顾客路线重新提升为主成长系统。
- 不让任务直接替代金币与累计口碑的店铺升级条件。
- 不增加旧任务 ID、旧任务进度或旧挑战快照的存档迁移；项目处于开发阶段，验证使用新存档。
- 不在本设计中重做任务面板的整体视觉布局。

## 4. 总体任务架构

任务分为五层：

| 层级 | 定位 | 是否阻塞成长 | 主要奖励 |
| --- | --- | --- | --- |
| 新手步骤 | 教会完整营业闭环 | 仅 Lv.0 阻塞 | 教学所需材料、少量金币 |
| 构筑课程 | 每次教授一个橱窗规则 | 不阻塞等级 | 金币、口碑、食谱星辉 |
| 阶段评鉴 | 检验多个规则的组合运用 | 不阻塞配方解锁 | 评级经验、称号进度、装饰性奖励 |
| 每轮目标 | 提供短期变化和重复游玩目标 | 完全可选 | 小额资源补给 |
| 资源支线 | 支撑库存、生产和自动化 | 完全可选 | 材料、种子、生产补给 |

店铺升级继续只由金币和累计口碑决定。任务可以提示玩家已经具备升级条件，但 Lv.1 以后不得用任务奖励直接设置等级，也不得以指定配方完成状态阻塞升级。

## 5. 阶段路线

### 5.1 Lv.0：第一次完整营业

Lv.0 是唯一强制顺序执行的阶段。玩家在进入 Lv.1 前必须完成一次完整闭环，而不是在第一次上架时立即结束教学。

推荐顺序：

1. 获得制作第一份商品所需的基础材料。
2. 制作第一份商品。
3. 把商品摆入橱窗。
4. 点击“开始营业”。
5. 观察至少一笔真实成交。
6. 打开本轮结算并处理剩余商品。
7. 完成结算后进入 Lv.1。

这一阶段可以使用固定教学商品保证流程稳定，但“固定教学商品”只服务于 Lv.0，不扩展为后续主线对指定配方的依赖。

“查看预计售价和待售时间”不作为独立任务、开始营业的前置条件或新手提示。玩家可以通过现有商品信息界面自行查看，但任务系统不记录 `showcase_terms_viewed` 事件，也不增加高亮、弹窗、气泡或按钮限制。上架任务完成后直接开放“开始营业”任务。

### 5.2 Lv.1：售速与补货

Lv.1 逐项教授营业节奏：

- 完成一次标准 30 秒营业轮。
- 让同一商品在一轮内售出两份。
- 商品进入待补货后，在营业中补入同款。
- 分别体验一次保留八折余货和五折直接清仓。
- 阶段评鉴：在不发生强制清仓的情况下达到基础销售目标。

每个课程只教授一个概念，不组合多个限制条件。玩家失败时直接指出未发生的操作或还差的数值。

### 5.3 Lv.2：基础构筑关系

Lv.2 从操作教学转向基础组合：

- 同时上架两种不同定位的商品。
- 触发一次布局额外收益或销售连锁。
- 在限定格数内达到目标金币。
- 根据营业前可见的环境调整一次橱窗。
- 阶段评鉴：完成一套包含引流、推进、放大或收割关系的基础构筑。

任务不得指定配方名称。条件使用商品角色、标签、占用格数、布局收益和营业结果，使玩家可以用当前已解锁内容寻找解法。

### 5.4 Lv.3–Lv.5：固定构筑评鉴

从 Lv.3 开始，主线只包含构筑挑战。每级由两项普通挑战和一项阶段评鉴组成：

| 等级 | 主题 | 主要考查内容 |
| --- | --- | --- |
| Lv.3 | 库存压力 | 待补货、轮内补货、余货和清仓控制 |
| Lv.4 | 连锁效率 | 多商品协同、连续成交、布局额外收入 |
| Lv.5 | 招牌构筑 | 环境适配、限制格数、高收益主题橱窗 |

Lv.3 后的主线定义中不得出现 `harvest`、`make_product`、`research_attempt` 或 `research_success` 作为完成事件。相关内容统一放入资源支线。

### 5.5 Lv.6+：长期挑战循环

Lv.6 起不再为每个等级编写固定主线。每次准备挑战轮时提供三个经营合同，玩家选择其中一个：

- 合同使用当前已开放机制和商品集合生成。
- 每个合同提供铜、银、金三级目标。
- 主题赛事可以改变环境、可用格数或商品条件。
- 最高评价推进门店评级和称号；金币只作为辅助奖励。
- 已完成合同可以使用不同构筑重复挑战和刷新成绩。

长期循环为：

> 选择挑战 → 调整构筑 → 30 秒营业 → 结算评级 → 获得称号进度 → 挑战更高目标

普通合同失败不扣长期成长。只有明确标注的 Lv.6+ 高风险合同允许收取保证金；教学、构筑课程和阶段评鉴均不收取保证金。

## 6. 任务条件模型

任务条件分为四类：

| 类型 | 用途 | 示例指标 |
| --- | --- | --- |
| 教学事件 | Lv.0–Lv.2 操作教学 | 制作、上架、开始营业、补货、完成结算 |
| 构筑快照 | 检查营业开始时的布局 | 占用格数、商品种类、角色、标签、区域、布局规则 |
| 营业结果 | 检查本轮最终成绩 | 成交数、金币、连锁收益、待补货、余货、清仓 |
| 连续表现 | 中后期进阶目标 | 连续成功轮数、累计评级、不同构筑完成数 |

条件支持 `all` 和 `any` 两种组合。前期课程只使用单条件；阶段评鉴和长期合同可以使用复合条件。例如：

> 使用不超过 8 格，在一轮内售出 6 件，并且强制清仓不超过 1 件。

任务只能引用已经进入统一营业报告的指标。新增条件类型时必须先补充报告字段、显示文案和判定测试，不能只在任务服务中临时读取其他运行状态。

## 7. 统一营业报告

每次完成结算时生成唯一营业轮报告，作为任务、挑战、结算弹窗和历史记录的共同输入。报告至少包含：

- 报告 ID、营业轮 ID、挑战 ID 和挑战版本；
- 营业类型、营业时长和本轮环境；
- 开始营业时的布局快照；
- 各商品成交数量、成交收入和最终售价来源；
- 总成交数、总金币和布局额外收入；
- 连锁触发次数和按类型拆分的连锁收益；
- 补货次数、补货数量和待补货次数；
- 八折余货、五折直接清仓和强制清仓数量；
- 占用格数、商品种类、角色和标签统计；
- 本轮是否完整结算以及报告完整性状态。

营业中展示的实时进度使用与最终报告相同的字段名和计算语义，但它只是临时预览。任务最终完成状态只在本轮完整结算后写入，避免中途退出或重复刷新造成误完成。

## 8. 配置与组件职责

### 8.1 配置来源

`game_data.json.tasks` 成为唯一任务目录，按以下分类保存完整定义：

- `tutorial_tasks`
- `build_courses`
- `stage_evaluations`
- `round_contracts`
- `resource_side_tasks`

每项任务定义包含 ID、版本、开放条件、前置条件、环境引用、任务条件、评级目标、奖励和完成提示。

`doc/showcase_round_rules.json` 只保存营业规则、环境参数和数值配置，不再单独维护一套挑战任务名称。任务通过环境 ID 引用规则配置，配置校验负责检查引用完整性。

### 8.2 运行组件

- `TaskService`：读取任务目录，决定开放状态、一次性进度、完成状态和奖励领取。
- `ShowcaseChallengeService`：根据任务定义与规则配置生成挑战快照，并使用营业报告计算评价。
- `ShowcaseRoundReportService`：生成唯一、完整的营业轮报告。
- `GameState`：保存当前教学步骤、已选择的合同快照、完成结果和待领取奖励。
- `TaskOverlay`：展示教学、构筑课程、阶段评鉴、经营合同和资源支线。
- 营业界面：显示当前挑战最多三个实时指标，不承担任务判定。
- 结算弹窗：同时显示营业结果、挑战评级、未达成原因和下一目标差值。
- `main_view.gd`：只协调任务选择、营业开始、实时刷新和结算结果，不继续拥有新的任务判定算法。

任务筛选 ID 由 `TaskOverlay` 单一维护。主视图只接收面板发出的筛选 ID 并刷新，不保存第二份筛选白名单；五个固定 ID 为 `main_course`、`contract`、`resource`、`automation` 和 `claimable`。即使某个分类当前为空，切换也必须生效，不能因旧 ID 校验把界面锁在上一个分类。

挑战快照必须保存任务 ID、任务版本、条件和环境参数。接受挑战后，即使开发期配置发生变化，本轮仍按接受时的快照结算。

## 9. 运行数据流

```text
读取任务配置
  → 检查等级、前置任务和已开放机制
  → 激活阶段任务或展示三个经营合同
  → 生成并保存本轮挑战快照
  → 开始营业
  → 使用统一字段刷新实时指标
  → 完成剩余品处理并生成最终营业报告
  → 挑战服务计算铜、银、金评价
  → TaskService 写入完成状态和待领取奖励
  → 结算弹窗显示结果与差距
  → 玩家领取奖励
```

Lv.0–Lv.5 的当前阶段任务自动激活。Lv.6+ 合同必须由玩家主动选择；没有已选合同时仍可开始普通营业，但不会产生合同评价。

## 10. 玩家反馈

任务必须在三个时点给出一致反馈：

### 10.1 营业前

- 显示本轮条件、奖励和铜银金目标。
- 对构筑快照条件进行预检查。
- 明确指出格数、角色、标签或库存条件不满足的原因。
- 不满足静态条件时允许玩家继续调整；普通营业不被任务条件阻塞。

### 10.2 营业中

- 最多固定显示三个实时指标。
- 使用“当前值 / 目标值”格式。
- 达成目标时提供清晰但不遮挡橱窗的状态变化。
- 不显示无法由营业中行为改变的冗余条件。

### 10.3 结算后

- 显示本轮获得的最高评价。
- 逐项显示达成与未达成条件。
- 说明距离下一评价的最小差距。
- 失败时给出可执行的调整方向，不只显示“挑战失败”。

示例：

> 银级达成；距离金级还差 18 金币。  
> 未达成原因：强制清仓 2 件，金级要求不超过 1 件。

## 11. 奖励规则

- 新手步骤提供下一教学步骤所需材料和少量金币，防止资源不足打断教学。
- 构筑课程提供金币、口碑和食谱星辉。
- 阶段评鉴提供评级经验、称号进度和橱窗装饰性奖励。
- 每轮目标只提供小额资源补给，不包含不可替代的永久解锁。
- 资源支线只提供材料、种子和生产补给，不提供门店评级。
- 同一报告 ID 和同一任务评价只能发放一次奖励。

## 12. 异常与边界处理

- 任务引用不存在的指标、环境、奖励类型或前置任务：配置校验失败，该任务不进入玩家列表。
- 玩家尚未解锁完成条件所需机制：任务不生成，不向玩家展示无法完成的目标。
- 营业报告缺少必要字段或未完成结算：挑战结果标记为无效，不判成功或失败，不消耗奖励机会。
- 同一结算 ID 重复应用：任务、评级和奖励均只处理一次。
- 玩家中途退出挑战轮：保留已接受快照和营业轮状态；只有完成结算后才写入任务结果。
- 挑战失败：保留差距说明并允许使用新营业轮重试。
- 配置版本变化：已接受挑战按快照版本结算，新挑战使用新版本。
- 旧存档：不做任务 ID 或进度迁移；开发验证删除旧存档并使用新游戏。

## 13. 验证标准

### 13.1 配置验证

- 所有任务 ID 唯一且版本为正整数。
- 所有前置任务、环境、指标和奖励引用存在。
- 每个任务至少有一个有效完成条件。
- 铜、银、金目标严格递增，且不存在更高评价反而更容易的条件。
- Lv.3 后主线不包含采集、制作和研发完成事件。

### 13.2 服务验证

- Lv.0–Lv.2 教学按既定顺序开放，不能跳过依赖步骤；Lv.0 上架后必须直接开放开始营业任务。
- 构筑快照、营业结果、连续表现和 `all` / `any` 复合条件均正确判定。
- 挑战快照在配置变化后仍按原版本结算。
- 同一报告不能重复推进任务或重复发奖。
- 缺失报告字段不会误判任务完成。

### 13.3 真实交互路径

- 新游戏可以完整走通 Lv.0 的制作、上架、营业、结算和升级，且不需要触发查看销售条款事件。
- Lv.1 可以通过真实营业路径完成待补货与轮内补货课程。
- Lv.2 可以完成一次真实布局或连锁收益课程。
- Lv.3–Lv.5 的阶段评鉴均可由当前等级已开放内容完成。
- Lv.6+ 可以从三个合同中选择一个，完成营业并获得正确评级。
- 任务面板、营业中指标和结算弹窗显示一致。

### 13.4 回归验证

- 标准营业仍固定为 30 秒，特殊挑战才允许使用其他时长。
- 营业轮补货、余货、清仓、金币和报告结果保持一致。
- 店铺升级仍只使用金币与累计口碑条件。
- 资源支线不会阻塞主线或等级升级。
- Godot headless 自检使用可写 `--log-file` 路径，并以退出码和显式 PASS 标记作为结果依据。

## 14. 实施边界

本设计可以作为一个完整实施计划，但实施时应按依赖拆分：

1. 先建立统一报告字段和配置校验。
2. 再建立任务目录、条件求值和评级模型。
3. 然后替换 Lv.0–Lv.5 任务路线并接通真实结算事件。
4. 最后增加 Lv.6+ 合同选择、三段反馈和完整回归。

不得为了让旧任务测试继续通过而恢复已废弃的顾客主线、旧挑战 ID 或旧任务完成语义。旧测试应随新任务合同一起更新。
